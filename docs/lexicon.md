# Lexicon: `com.foto-log.photo`

Each photo on a fotolog is a `com.foto-log.photo` record in the poster's own ATProto repo (on their PDS). The schema is in [`lexicons/com/foto-log/photo.json`](../lexicons/com/foto-log/photo.json).

## Record key

The record key is the **upload date** in the poster's time zone, written as `YYYY-MM-DD` (for example `at://did:plc:…/com.foto-log.photo/2026-10-06`). This guarantees at most one photo per calendar day per user: writing a second photo for the same day would replace the first. The lexicon declares the key type as `any`, so the key format is checked in code by `assertValidPhotoRecord`.

## Fields

| Field | Required | Notes |
|---|---|---|
| `post` | yes | `com.atproto.repo.strongRef` to the `app.bsky.feed.post` that shares the photo. Replies to that post are the photo's guestbook. |
| `image` | yes | Blob, `image/*`, at most 1,000,000 bytes. |
| `alt` | no | Alt text, up to 1000 graphemes. |
| `aspectRatio` | no | `{ width, height }`, both integers ≥ 1. |
| `caption` | no | Up to 300 graphemes (and 3000 bytes), the same as a Bluesky post. |
| `uploadDate` | yes | `YYYY-MM-DD`, the day the photo was posted, in `timeZone`. Equals the record key. |
| `displayDate` | yes | `YYYY-MM-DD`, the day the photo is shown under. **Always equals `uploadDate` in v1.** Letting users choose it is deferred. |
| `timeZone` | yes | IANA time zone name, e.g. `America/New_York`. |
| `createdAt` | yes | ATProto datetime (with a time zone offset). |

## Code

- `lib/photo-record.ts`:
  - `buildPhotoRecord()` builds a record and its key from a `Date` and an IANA time zone, then validates it.
  - `assertValidPhotoRecord()` validates a record read from a repo. On top of the lexicon checks, it requires real calendar dates, a known time zone, an image blob within the type and size limits (the lexicon validator doesn't enforce those), and the v1 rule that the record key, `uploadDate` and `displayDate` all match.
- `lib/lexicon/` is generated by `npm run lex:gen` from everything in `lexicons/`. Don't edit it by hand; CI fails if it's out of date. The `com.atproto.repo.*` lexicons are copied from [bluesky-social/atproto](https://github.com/bluesky-social/atproto/tree/main/lexicons/com/atproto/repo) because the generated client refers to them.

## Changing the schema

ATProto lexicons have to stay backward compatible once records exist: no new required fields, no removed fields, and no tightened constraints. New fields must be optional.

## Publishing

The lexicon isn't published for automatic resolution yet. That needs a foto-log account DID to hold the schema record and a `_lexicon.foto-log.com` TXT record. Tracked in a follow-up issue.
