# Sign-in (ATProto OAuth)

foto-log signs people in with their existing ATProto account (Bluesky or any other PDS) using [ATProto OAuth](https://atproto.com/specs/oauth) via `@atproto/oauth-client-node`.

## Flow

1. `/login`: the user enters a handle, or leaves it blank to use Bluesky (`https://bsky.social`). The `signIn` server action calls `client.authorize()`, which resolves the account's authorization server, makes a pushed authorization request, and redirects there.
2. The user approves on their own server (foto-log never sees their password).
3. `/oauth/callback`: exchanges the code for tokens, stores the OAuth session, looks up the handle on the user's PDS (`com.atproto.repo.describeRepo`), creates a browser session and sets the cookie.
4. Sign out (header button) deletes the browser session. If it was the account's last one, it also revokes the OAuth tokens with the user's server.

## Scopes

Defined in `lib/oauth/scopes.ts`. We ask for granular permissions first:

```
atproto repo:com.foto-log.photo repo:app.bsky.feed.post repo:app.bsky.feed.threadgate blob:image/*
```

That's enough to write photo records, the Bluesky post that shares each photo, guestbook replies, threadgates (to close a guestbook), and image uploads, and nothing else. If the user's authorization server rejects that with `invalid_scope` (whether up front at PAR or later at the callback), we retry once with `atproto transition:generic`. The client metadata declares both.

## Client

| | Production | Local dev |
|---|---|---|
| Client type | Confidential (`private_key_jwt`, ES256) | Loopback (`http://localhost?...`), public |
| `client_id` | `https://foto-log.com/oauth/client-metadata.json` | generated by `buildAtprotoLoopbackClientMetadata` |
| Redirect URI | `https://foto-log.com/oauth/callback` | `http://127.0.0.1:3000/oauth/callback` |
| JWKS | `https://foto-log.com/oauth/jwks.json` (public key only) | none |

Production mode is on when `PUBLIC_URL` is set.

## Storage

All in Postgres (`lib/db/schema.ts`):

- `oauth_state`: in-progress sign-ins, deleted after an hour.
- `oauth_session`: token sets and DPoP keys, one row per account DID.
- `user_session`: one row per signed-in browser, expires after 30 days.

`oauth_state.value` and `oauth_session.value` are encrypted with AES-256-GCM (`lib/crypto.ts`), using the row key as associated data so a value can't be copied to another row. Token refreshes take a Postgres advisory lock, so two Cloud Run instances never refresh the same session at once.

## Cookie

`__Host-fotolog_session` (in dev, `fotolog_session`): HttpOnly, Secure, SameSite=Lax, Path=/, 30 days. Its value is a random 256-bit session ID signed with HMAC-SHA256. The cookie holds no account data.

## Secrets

| Env var | Secret Manager secret | What |
|---|---|---|
| `OAUTH_PRIVATE_KEY` | `oauth-private-key` | ES256 private JWK (kid `foto-log-2026-10`) |
| `COOKIE_SECRET` | `cookie-secret` | 32 random bytes, base64: cookie signing |
| `STORE_ENCRYPTION_KEY` | `store-encryption-key` | 32 random bytes, base64: encrypts OAuth state and sessions |
| `DB_PASSWORD` | `db-password` | password for the `fotolog` database user |

In production a missing secret is a startup error. In dev, built-in dev values are used.

### Rotating the OAuth key

Add a second key to the keyset (both are published in the JWKS), deploy, then remove the old one after existing sessions have refreshed. Changing `STORE_ENCRYPTION_KEY` makes every stored OAuth session unreadable, so everyone has to sign in again.
